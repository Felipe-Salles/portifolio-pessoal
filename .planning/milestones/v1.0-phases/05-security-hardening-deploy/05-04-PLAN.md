## Phase Goal

**As a** visitor (recruiter, client or peer) landing on Felipe's portfolio, **I want to** reach the site at a public HTTPS address whose browser-enforced security headers block framing, script injection and protocol downgrade, **so that** the site itself is the proof that its author takes technical security seriously.

This plan proves the slice from the visitor's side: not "the headers are present" but "a real browser applies them and the site still works".

<objective>
Add a real-browser gate that loads the production URL, asserts zero CSP violations and exercises the mobile nav toggle under the enforced policy, then take a blocking human sign-off on the live site and an independent third-party header scan.

Purpose: `scripts/verify-deploy-headers.mjs` proves the six headers are present, but a header check cannot detect the failure mode that actually matters for D-04's enforce-from-the-start decision — an enforcing CSP silently blocking `Nav.astro`'s inline script and leaving the mobile menu dead. That only surfaces in a browser. Playwright is already a devDependency (used by `verify-a11y.mjs` and `generate-og-image.mjs`), so this costs no new dependency.
Output: one new standalone gate script and a signed-off production site.
</objective>

<!-- Gate contract (same as every verify-*.mjs in this repo). -->

1. `#!/usr/bin/env node` shebang, then a block comment naming the requirement IDs gated,
   the dependency policy, and the literal summary-line format.
2. A hard precondition guard that prints a fixed message and exits 1 (here: the missing
   URL argument, following scripts/verify-deploy-headers.mjs rather than the dist/ guard).
3. Accumulate every finding into a `violations` array — never exit on the first failure.
4. Print each violation to stderr with a consistent per-line prefix.
5. Print exactly ONE fixed-format summary line to stdout as the last line before exit.
6. `process.exit(0)` only when violations is empty.

The one inline script the enforced CSP must not block (src/components/Nav.astro):
  A `<script>` with no unprocessed-script opt-out attribute, so Astro bundles and inlines
  it. It is the mobile overlay controller. Its observable contract, from Phase 2:
    - The toggle element carries the attribute `data-nav-toggle`.
    - The overlay element has id `nav-overlay`.
    - Opening sets `data-menu-open="true"` on the `<nav>`, on `#nav-overlay` and on
      `<body>`; closing sets it back to `"false"` on nav/overlay and removes it from body.
  If the CSP blocks the script, clicking the toggle changes none of those attributes.

Playwright usage already established in this repo: see scripts/verify-a11y.mjs for the
chromium launch/teardown shape and how it reports per-page findings.

Composite verify chain after plans 05-01 and 05-02 — this plan's script does NOT join it
(it needs a live URL), exactly like verify:deploy.

    Create `scripts/verify-live-csp.mjs` as Node ESM. It may import `chromium` from the already-installed `playwright` devDependency — that is the single permitted non-builtin import, matching `scripts/verify-a11y.mjs`; everything else must come from `node:` builtins.

    Take the production URL from `process.argv[2]` into one named binding used everywhere; never duplicate a domain literal in the file. If the argument is absent, print exactly `usage: node scripts/verify-live-csp.mjs <production-url>` to stderr and exit 1. If the URL protocol is not `https:`, record a violation named `https` and exit 1 without launching a browser.

    Launch headless chromium. Before each navigation, install a collector with `page.addInitScript` that registers a `document.addEventListener("securitypolicyviolation", ...)` handler pushing `{ violatedDirective, blockedURI, sourceFile, lineNumber }` onto a global array on `window`. Also subscribe to the page's `console` events, keeping any message of type `error`, and to `pageerror` events, keeping the error message — a CSP block on a module script surfaces as a console error phrased "Refused to execute…" rather than always producing a violation event, so both channels are needed.

    Visit two pages at a mobile viewport of 390x844: the production root, and the production origin plus `/__gsd-404-probe` to exercise the custom 404. Wait for the network to go idle before reading results. For each page, read the collected violation array back out with `page.evaluate` and record:
    - `csp-violation`: one violation per collected `securitypolicyviolation` entry, naming the violated directive and blocked URI.
    - `console-error`: one violation per captured console error or page error, with its text truncated to a single line.

    On the root page only, exercise the inline script to prove it executed under the enforced policy: assert an element matching `[data-nav-toggle]` is present, click it, wait for `#nav-overlay` to carry `data-menu-open="true"`, then click it again and wait for that attribute to become `"false"`. Record a violation named `inline-script-blocked` if the toggle is absent, if either state transition does not happen within a short timeout, or if the click itself throws — this is the exact symptom of an enforcing CSP whose `script-src` hash no longer matches the shipped script.

    Also assert on the root page that `document.title` is non-empty and that a `<main>` landmark exists, so a CSP-driven blank render cannot pass silently.

    Always close the browser in a `finally` block. Print each violation to stderr as `verify-live-csp: <check> — <detail>`, then exactly one summary line to stdout: `LIVECSP SUMMARY url=<url> pages=<n> csp_violations=<n> console_errors=<n> nav_toggle=<ok|fail> violations=<n>`. Exit 0 only when violations is empty.

    Then add `"verify:live-csp": "node scripts/verify-live-csp.mjs"` to package.json scripts after `audit:ci`. Do NOT add it to the composite `verify` chain — like `verify:deploy` it requires a live URL argument.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Enforced CSP → the site's own inline script | An enforcing policy (D-04) can break the site it is protecting; a header-presence check cannot detect that |
| Automated gate → human judgement | Every machine check can pass while the page renders blank or broken |
| This project's gates → an independent scanner | Self-graded security is a weaker claim than an outside scan of the same live URL |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-04-01 | Denial of Service | The enforcing CSP blocking `Nav.astro`'s inline script, leaving the mobile menu dead for every phone visitor | mitigate | `scripts/verify-live-csp.mjs` clicks the real toggle on the live site at a 390x844 viewport and asserts the `data-menu-open` state transitions both ways, recording `inline-script-blocked` otherwise; the human checkpoint repeats it by hand |
| T-05-04-02 | Tampering | A CSP violation that produces a console error but no `securitypolicyviolation` event going unnoticed | mitigate | The gate subscribes to `securitypolicyviolation`, `console` error messages and `pageerror` simultaneously, and treats any of the three as a violation |
