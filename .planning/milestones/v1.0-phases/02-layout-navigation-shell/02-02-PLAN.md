<constraints>
**Do NOT introduce a UI framework island.** No React, Vue, Svelte, Preact, Solid, Alpine, or any `client:*` directive. ROADMAP Phase 2 success criterion 2 says "vanilla JS only", and CLAUDE.md's stack guidance says complexity only when necessary. One co-located `<script>` inside `Nav.astro` is the entire budget.

**Do NOT install any npm package.** Zero dependencies are added by this plan.

**Do NOT author the script with `is:inline`.** A bare `<script>` in a `.astro` file is processed and bundled by Astro, which is what keeps it compatible with the `script-src 'self'` CSP that Phase 5 (SEC-02) must ship. `is:inline` opts out of that processing entirely.

**Do NOT nest the overlay inside the `<nav>` element.** The nav carries `backdrop-blur-xl`, and a non-`none` `backdrop-filter` makes an element a containing block for `position: fixed` descendants — an overlay with `fixed inset-0` placed inside the nav would be clamped to the nav bar's own box instead of covering the viewport. The overlay is a sibling of `<nav>` inside `Nav.astro`'s template.

**Do NOT use the `hidden` HTML attribute to hide the overlay.** The overlay carries Tailwind's `flex` utility, an author-level `.flex { display: flex }` rule that beats the user-agent `[hidden] { display: none }` rule. Hiding must come from the author-level attribute selector specified below.

**Do NOT touch `src/layouts/Base.astro`, `src/pages/index.astro`, `src/components/Footer.astro`, or `package.json`.** The body scroll lock is applied by setting an attribute on `document.body` from the script, not by editing the layout. `Footer.astro` and the `Base.astro` footer mount belong to plan 02-03.

**Do NOT build any content section, and do NOT create the `#dossier`/`#stack`/`#projects`/`#contact` targets.** Still Phase 3.

**Do NOT change the desktop nav, the brand wordmark, the skip link, or the `:focus-visible` primitive.** Those shipped in 02-01 and their gate checks must keep passing unchanged.
</constraints>

| Boundary | Description |

| build-time markup → client-side script execution | This plan introduces the first executable JavaScript in the project. Everything that ships to the browser and runs there is a new attack surface class that did not exist in Phase 1. |
