## Phase Goal

ROADMAP Phase 2 goal, quoted verbatim (see plan 02-01's note — the roadmap goal is not written in the three-slot user-story form and is not restated here as an invented one):

> Visitor loads any page and sees the correct site shell — navigation, footer, and page metadata — matching the design system, in Portuguese, and fully keyboard-accessible.

This plan delivers the last piece of that shell: the footer band that closes every page.

<objective>
Complete the site shell with a footer: a low-emphasis band carrying a dynamic copyright line and a row of link labels sourced from `site.socials` (D-03), mounted below `<main>` in the shared layout. Close out the Phase 2 gate with footer and heading-hierarchy assertions.

Purpose: The footer is the last thing a visitor sees and the second place (after the future Contact section) that social links appear. Driving it from `site.socials` now means replacing placeholder links in v2 is a one-file edit rather than a hunt through markup, and it prevents the footer and the Phase 3 Contact section drifting apart. This plan also closes the one clause of A11Y-01 nothing else covered — heading hierarchy.
Output: `src/components/Footer.astro`, the completed `Base.astro` shell, and a fully green `npm run verify:shell` covering the whole Phase 2 contract.
</objective>

<constraints>
**Do NOT hardcode footer link labels.** D-03 is explicit: the row is a map over `site.socials`, not a parallel list. The prototype's literal `GitHub` / `LinkedIn` / `Documentation` anchors are replaced, not preserved, and the row will render four entries (however many `site.socials` has), not three.

**Do NOT use `site.socials[].icon` in the footer.** Text labels only. Icons are the Phase 3 Contact section's treatment.

**Do NOT use `font-mono-code` / `text-mono-code` anywhere in the footer.** The prototype styles the link row with the 13px/400 `mono-code` token while the copyright line uses 14px/500 `mono-label`. Carrying both would introduce a third font weight and break the project's two-weight typography budget, so the UI-SPEC Typography section collapses both footer text blocks onto `mono-label`. `mono-code` stays a valid token for Phase 3, just not here.

**Do NOT port the prototype's copyright text.** `© 2024 SYSTEM_ARCHITECT // ALL RIGHTS RESERVED` is fictional persona copy. The replacement is specified in the action and uses a build-time year plus the existing `site.brand` placeholder — no new `site.ts` field.

**Do NOT add a contact form, a newsletter input, or any interactive footer element.** A functional contact form is in REQUIREMENTS.md's Out of Scope list; the footer must not grow a shape that invites one.

**Do NOT install any npm package, and do NOT add a `<script>` to `Footer.astro`.** The footer is fully static.

**Do NOT touch `src/components/Nav.astro`, `src/styles/global.css`, `src/pages/index.astro`, or `package.json`.** Plans 02-01 and 02-02 own those and their gate checks must keep passing unchanged.

**Do NOT create a 404 page** — Phase 4 (A11Y-02), even though it will reuse this exact shell.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo-authored data (`site.socials`) → rendered anchor `href` attributes | The footer is the first place in the project where repo data flows into an attribute rather than into text content. Attribute contexts have different escaping and different abuse cases than text contexts — a URL sink is a script-execution sink if its scheme is attacker-chosen. |
| footer links → third-party origins (future) | The `href` values are `"#"` today and become real external social URLs in v2 (REAL-03). The link markup shipped now determines whether that transition is safe by default or requires someone to remember a security attribute. |
| placeholder copy → production output | The prototype's fictional copyright line would be plausible enough to survive review and ship. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-02-16 | Tampering (XSS via URL sink) | `site.socials[].href` bound to an anchor `href` | mitigate | Astro escapes the attribute value, but escaping does not stop a `javascript:` scheme, which would make the footer a script-execution sink. The values are build-time constants authored in this repository, never user input, and Phase 5's `npm audit` / no-secrets review (SEC-04) covers the repo-authored surface. The durable control is that these values have exactly one home (`src/data/site.ts`), so the Phase 3 Contact section and this footer cannot diverge and only one file ever needs review. | T-02-17 | Tampering (reverse tabnabbing) | Footer social anchors, once they carry real external URLs | mitigate | `rel="noopener noreferrer"` is applied to every footer social anchor now, while the hrefs are still inert placeholders, so the control cannot be forgotten when REAL-03 swaps in real URLs. | T-02-18 | Tampering (XSS) | `site.brand` and `site.socials[].label` rendered as footer text | mitigate | Both are interpolated with plain Astro expressions, which HTML-escape by default. `set:html` is banned by `<constraints>` and its absence in `Footer.astro` is asserted by both the Task 2 verify command and the gate. |
