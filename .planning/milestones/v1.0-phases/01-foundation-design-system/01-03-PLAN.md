Create `src/content.config.ts` — at the root of `src/`, not inside `src/content/`. Import `defineCollection` and `z` from `astro:content` and `glob` from `astro/loaders`. The `schema` must be a *function* of the form `({ image }) => z.object({ … })`, never a plain `z.object({ … })`. The `image` helper is injected by Astro into that function and is not otherwise in scope; using the plain-object form produces a `ReferenceError: image is not defined` (RESEARCH.md Pitfall 6). If the `z` re-export from `astro:content` does not resolve, fall back to importing `z` from `astro/zod` — both paths are reported to work and the failure is a loud missing-export error caught immediately at this file (RESEARCH.md Assumption A2).

Field set, combining what REQUIREMENTS.md needs in Phase 3 with the two forward-looking fields locked in D-04:
- `title` — required string (PROJ-02: card name)
- `description` — required string (PROJ-02: card description)
- `tags` — required array of strings (PROJ-02: tech tags)
- `liveUrl` — optional URL-validated string (PROJ-02: independently optional per the prototype's card 2)
- `repoUrl` — optional URL-validated string (PROJ-02: independently optional per the prototype's card 3)
- `coverImage` — optional, typed with the `image()` helper (D-05). Typing it through `image()` from Phase 1 onward is what makes PROJ-04's `astro:assets` optimisation available at render time in Phase 3 without a schema change.
- `featured` — optional boolean (D-04): lets Phase 3 decide card hierarchy without a later migration
- `order` — optional number (D-04): manual display ordering, independent of filename or alphabetical sort

Replace the `scripts/verify-content-schema.mjs` stub with the real gate — dependency-free Node ESM, using `node:fs`, `node:path`, and `node:child_process`. Contract:
- **Location check:** assert `src/content.config.ts` exists and that `src/content/config.ts` does *not*, since the legacy path silently yields an empty collection.
- **Shape check:** read `src/content.config.ts` as text and assert the `schema` is declared in the injected-function form (a `schema:` key whose value destructures `image` from an object parameter and returns), that the `glob` loader is used with base `./src/content/projects`, and that all eight field names are present.
- **Positive test:** run `npx astro build` as a subprocess. It must exit 0 — the valid placeholder entry passes validation.
- **Negative test:** this is the part that actually proves enforcement. Write a temporary probe file `src/content/projects/__schema-probe.md` whose frontmatter deliberately omits the required `description` field, run `npx astro build` again, and require it to exit non-zero. Delete the probe in a `finally`-style cleanup so it is removed whether the build fails, succeeds, or throws — leaving it behind would poison every later build. Fail the whole gate with a clear message if the build *succeeded* with the invalid probe present, because that means the schema is not being enforced at all.
- **D-03 convention check:** read `src/content/projects/*.md` and, once it exists, `src/data/site.ts`, and assert that neither contains any of the prototype's fictional strings — `SYSTEM_ARCHITECT`, `ARCHITECT`, `SYSTEM.CORE`, `Neural Engine`, `Vault-X`, `Omni-Stream`, `AVAILABLE FOR NEW PROJECTS` — and that each file contains at least one `PLACEHOLDER` marker or bracketed `[…]` marker. Skip the `src/data/site.ts` half gracefully if the file does not exist yet, so this task's own verification passes before Task 2 creates it.
- Print a summary line `SCHEMA SUMMARY location=ok shape=ok positive=<pass|fail> negative=<pass|fail> placeholders=<n>_files_ok`. Exit 0 only when every check passes.
- Note the runtime cost: this gate runs two full Astro builds. For a site with one page that is a few seconds, which is acceptable for the confidence it buys.
